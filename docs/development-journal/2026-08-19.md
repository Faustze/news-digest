## [Architecture Decision] Serverless-first: GitHub Actions как оркестратор, JSON вместо БД

Date: 2026-08-19
Area: architecture
Story: serverless-architecture

Context:
Один пользователь, нет бюджета/VPS, нужен zero-maintenance инструмент.

Alternatives:
- VPS + всегда-включённый бот/сервис — дороже и требует обслуживания;
- webhook-сервер для Telegram — противоречит «нет backend».

Decision:
Вся логика живёт в GitHub Actions cron; персистентность — JSON-файлы
(user-profile.json, feedback.json, output/); Telegram-обратная связь опрашивается
через getUpdates без webhook.

Reason:
Минимальная стоимость и обслуживание; single-user не требует серверных мощностей.

Trade-offs:
- нет real-time: дайджест только по расписанию;
- feedback собирается только в момент запуска workflow;
- упираемся в лимиты free-тиров (Groq TPD, GitHub Actions minutes).

Consequences:
Вся продуктивная логика должна работать без постоянного процесса; любые новые
компоненты должны помещаться в workflow.

## [Architecture Decision] Фабрика LLM-провайдеров (groq/openai/anthropic/ollama)

Date: 2026-08-19
Area: LLM
Story: llm-provider-abstraction

Context:
Изначально классификация и суммаризация были жёстко завязаны на Groq.
Появилось желание переключать провайдера (локальная разработка без ключа, лимиты free-тира).

Alternatives:
- оставить Groq захардкоженным — просто, но vendor lock-in;
- конфиг-файл с провайдером и фабрикой — чуть больше абстракции, но переключение одним полем.

Decision:
news/llm.py: build_llm(config) возвращает BaseChatModel по конфигу; SUPPORTED_PROVIDERS =
(groq, openai, anthropic, ollama); дефолтные модели на провайдера; ollama — без ключа.

Reason:
Переключение провайдера без изменения кода; локальная разработка через ollama;
fallback при исчерпании free-тира.

Trade-offs:
- появился слой абстракции над LLM;
- у каждого провайдера свои дефолтные параметры (max_tokens, num_predict);
- поведение разных провайдеров может различаться.

Consequences:
config.yaml получил provider/model/temperature/max_tokens; фабрика используется в
pipeline и в тестах (test_llm.py).

Potential content:
true

Content angle:

## [Architecture Decision] Детерминированная дедупликация до LLM

Date: 2026-08-19
Area: ingestion / RSS
Story: rss-deduplication

Context:
Одна и та же статья встречалась в дайджесте несколько раз: разные фиды отдают
одинаковый контент с разными URL.

Problem:
Дубли раздували дайджест и стоили токенов на классификацию.

Investigation:
Обнаружено, что разные RSS-фиды экспонируют разные URL для одной статьи
(query-параметры, регистр, trailing slash).

Decision:
Дедупликация выполняется детерминированно ДО LLM (news/deduplicate.py):
- нормализация URL (lowercase host/path, срезка query/fragment/trailing slash);
- нормализация заголовка (lowercase, без пунктуации, схлопывание пробелов);
- Jaccard-похожесть заголовков с порогом 0.6;
- порядок проверок: news_id → URL → title → similarity.

Reason:
Дешёвые детерминированные проверки отсекают большинство дублей до дорогого LLM;
нормализация URL появилась по ревью CodeRabbit (query/fragment/trailing slash).

Lesson:
Детерминированная дедупликация должна идти до LLM-обработки.

Potential content:
true

Content angle:

## [Problem] Groq 429 (TPD 100K) ронял весь пайплайн

Date: 2026-08-19
Area: LLM / pipeline
Story: groq-rate-limit

Symptom:
Pipeline падал с Groq 429 (token-per-day лимит free-тира) — один rate-limit убивал весь прогон.

Initial hypothesis:
Транзиентная ошибка сети; достаточно повтора.

Investigation:
Ошибка возникала при превышении дневного лимита токенов; payload классификации был
избыточным (полный summary, link, отступы в JSON), max_tokens был 4096.

Root cause:
Превышен дневной budget токенов free-тира; классификатор не обрабатывал
RateLimitError, исключение всплывало и прерывало прогон.

Decision:
- groq.RateLimitError ловится: лог, оставшиеся батчи accepted=false, stop;
- прочие groq.GroqError/httpx/timeout: лог и continue со следующими батчами;
- компактный payload: summary урезается до 250 символов, link не шлётся,
  categories_json без отступов, пауза 2s между батчами;
- max_tokens 4096 → 2048.

Result:
Прогон переживает rate-limit; при исчерпании лимита оставшиеся батчи получают
accepted=false, 0 принятых статей → пустой дайджест не создаётся и не отправляется,
прогон не падает.

Lesson:
Ошибки LLM-провайдера никогда не должны ронять весь дайджест; free-тир требует
контроля размера payload.

Potential content:
true

Content angle:
Как Groq free tier сломал мой пайплайн (и что я сделал)

## [Problem] Категория из feedback не маппится на canonical id — сигнал не влияет на ранжирование

Date: 2026-08-19
Area: telegram / feedback / ranking
Story: feedback-category-mapping

Symptom:
Реакции 👍/👎/🔕, судя по всему, почти не влияли на дайджест.

Initial hypothesis:
Сигнал слишком слабый (дельты ±0.1), эффект незаметен.

Investigation:
Трассировка цепочки render → parse → poll:
- render_telegram выводит подпись #CATEGORY_LABELS (русские подписи, например
  «Технологии», «Бег и тренировки»);
- parse_items_from_digest берёт первое слово подписи через #(\S+): «Технологии»,
  «Бег», «Кино»;
- build_callback_data кладёт эту строку в callback_data;
- apply_reactions сохраняет в feedback.json category = строка.lower() — «технологии»,
  «бег», «кино».

Root cause:
Нет обратного маппинга «русская подпись → canonical id». В rank._category_feedback_scores
группировка идёт по reaction.category («технологии»), а rank_item ищет category_scores
по canonical id («technology»). Совпадает только «AI» → «ai» (11 из 12 категорий
никогда не получают feedback-поправку).

Result:
Проверено скриптом: для 11/12 категорий сохранённая категория не равна canonical id
(«Бег и тренировки» → «бег», «Кино и сериалы» → «кино» и т.д.).

Decision:
В тестовой сессии добавлен обратный маппинг _resolve_category_id (по первым словам
CATEGORY_LABELS → id) в poll_feedback.py; тесты (113) зелёные, маппинг проверен.
Изменение откачено после теста — баг остаётся открытым, кандидат на реальный фикс.

Lesson:
User-facing подписи и внутренние id должны разводиться на границе рендера, а не в момент
сохранения реакции.

Potential content:
true

Content angle:

## [Technical Decision] DELETE для repository-слоя — CRUD доведён до конца

Date: 2026-08-19
Area: persistence / repositories
Story: repository-crud

Context:
Репозитории (User/Article/Feedback, raw SQL через sqlalchemy.text) имели только
INSERT (get_or_create/upsert/create), SELECT и UPDATE (через ON CONFLICT DO UPDATE).
DELETE отсутствовал.

Decision:
Добавлены точечные DELETE-методы, зеркалящие существующие access-паттерны:
- ArticleRepository.delete_by_id / delete_by_url → bool
- FeedbackRepository.delete_feedback(user_id, article_id) → bool
- UserRepository.delete_by_telegram_id → bool

Все методы используют `RETURNING id ... scalar_one_or_none()` и возвращают bool
(удалено или нет) — тот же приём, что get_or_create.

Consequences:
CRUD по трём таблицам закрыт. FK без ON DELETE CASCADE: удаление article/user с
существующим фидбеком упадёт на IntegrityError — осознанно не решалось, в текущем
usage-паттерне не требуется.

Result:
pytest: 120 passed (было 113/116), включая 4 новых теста DELETE; ruff check/format чисто.
Postgres поднят через docker compose для интеграционных тестов.

Potential content:
false

## [Architecture Decision] Нормализация URL перед INSERT — UNIQUE по articles.url начинает защищать от дублей RSS

Date: 2026-08-19
Area: persistence / repositories
Story: rss-url-uniqueness

Context:
UNIQUE constraint на articles.url существовал с первой миграции (articles_url_key),
но защищал только от ПОЛНОСТЬЮ одинаковых строк. RSS-дубли приходят с разными
query-параметрами (utm_source/utm_medium) или case/слэшами — raw URL отличался,
get_or_create вставлял вторую строку, и БД-уровневая защита не срабатывала.
Дедупликация жила только в памяти (deduplicate._normalize_url), до БД не доходила.

Decision:
Нормализация URL вынесена из deduplicate.py в общий news/url_utils.normalize_url
(дублирование появилось → модуль оправдан) и применяется в
ArticleRepository.get_or_create ДО INSERT и в SELECT-fallback, а также в delete_by_url.
Теперь два фида с одной статьёй (разные utm-метки) упираются в один и тот же
normalized url → ON CONFLICT (url) DO NOTHING возвращает существующий id.

Alternatives:
- Просто объявить задачу «уникальность уже есть» — не решает проблему tracking-дублей.
- Дедупликация только в памяти — не защищает персистентный слой.

Consequences:
Хранимое значение url — нормализованное (без query/fragment, lowercase, без слэша).
Тесты URL-нормализации переехали в tests/test_url_utils.py; интеграционный тест
проверяет, что get_or_create с utm-URL и с case-вариантом возвращает один id.

Result:
pytest: 121 passed; ruff check/format чисто.

Potential content:
true

Content angle:
Почему UNIQUE constraint не защищал от дублей RSS и как одна функция закрыла дыру
